# MyPetPair implementation research

- Decision: Expo universal client. Rationale: shared UI and behavior across all requested targets, DOM-backed React Native Web and native capability modules. Alternatives: Flutter and separate native/web; trade-offs in `docs/ARCHITECTURE.md`. Source: https://docs.expo.dev/workflow/web/ and https://docs.flutter.dev/platform-integration/web/faq.
- Decision: Java 17 / Spring Boot 3.5 maintained patch resolved from official Maven repository at implementation. Rationale: installed JDK and mature ecosystem. Use explicit dependencies/lockfiles, record actual versions. Alternative: Boot 4 requires migration APIs with little pilot benefit.
- Decision: opaque hashed bearer sessions with BCrypt. Rationale: straightforward revocation, no signing-secret management, one same-origin web host. Web memory tokens, native SecureStore; no localStorage tokens. Alternative: managed OIDC may replace sessions before open launch.
- Decision: SQL transactions serialize request/consent/block actions against a lock row, with durable active-pair uniqueness or equivalent serialization. Rationale: contact privacy must hold during concurrency; avoid in-memory-only invariants.
- Decision: store only coarse coordinates and distance bands; owner-selected dog is search center. Rationale: avoid arbitrary probe endpoints and reduce home-location exposure. Quantization is risk reduction, not anonymity.
- Decision: manually reviewed self-declared health summaries and owner vet attestations. Rationale: professional suitability cannot be inferred from breed/age. Pilot 24-month floor is provisional. No raw veterinary documents collected. Source: https://www.aspca.org/about-us/aspca-policy-and-position-statements/position-statement-criteria-responsible-breeding.
- Decision: gated signup with invitation secret; email ownership verification/recovery is a public-launch dependency because no email provider exists yet. No verified-email claims. Alternative: fake verification would be misleading.
- Decision: Cloud Run + Cloud SQL PostgreSQL + Secret Manager. Rationale: durable relational state and managed deployment; fixed SQL cost accepted for pilot. Cost sources in architecture document. Billing enabled and target project identity verified read-only.
